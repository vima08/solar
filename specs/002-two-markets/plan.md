# План 002 — Два рынка

Статус: awaiting-playtest. Спецификация и этот план одобрены владельцем 2026-11-01 после независимого READY для обсуждения. Реализация согласованных цен и T9 завершена; проверки записаны в review.md, физический планшет и игровой опыт ожидают владельца.

## Подход

1. T1–T4/T6/T9: новый чистый `js/game/markets.js` хранит порты/товары/цены и переходы buy/sell. Передавать место посадки и актуальное состояние явно. Хранить рыночный груз отдельно от неприкосновенной аппаратуры; общий usedSpace = contractCargo + marketCargo + активный курьерский груз. Этот же счётчик использовать при принятии исходного контракта и подработки, а не только при покупке. Для двух мест достаточно списка единиц `{ goodId, purchasePrice }`; продажа использует FIFO среди единиц выбранного товара, прибыль = местная цена продажи минус purchasePrice. Журнал хранит последнюю успешную сделку, не бесконечную историю.
2. T5: добавить commit(nextState) в единый store: при issue/retired отказать, иначе записать целый снимок атомарно, затем изменить текущий объект состояния, сохраняя его identity для экспедиции/UI. Удалять отсутствующие в новом снимке поля, обновлять raw и уведомлять после завершения. При исключении не менять память. До сделки синхронизировать текущее положение корабля. Не переиспользовать схему «изменить память и затем save», допустимую ранее для полёта, как гарантию атомарной торговли.
3. T7/T9: career версии2 добавляет marketCargo, последнюю сделку и reliefContract. Все career1 мигрируют в2 с пустым рыночным грузом, lastTrade=null и idle-подработкой, сохраняя деньги/контракт. Файловый envelope версии2 принимает v1 через миграцию; v2 экспортирует новые поля. Старые сборки видят career2 как будущую и не затирают её. Обновить normalizer, validateExpedition, reset, export/import и фикстуры вместе. Повреждённые/переполненные новые данные не исправлять молчаливым удалением товара: локальный барьер с исходной копией, импорт отклоняется.
4. T1/T2/T8: панель рынка в пульте показывает текущий порт, баланс, использованные места, остатки и две разные кнопки «Купить за…» / «Продать за…». В другом месте — объяснение и выбор порта. Интерфейс транзакций обновляется по событиям, без покадрового пересчёта DOM. Сравнение цен не требует перелистывать длинные таблицы на планшете.
5. T3–T9: тесты точных сумм, общего трюма при принятии обоих контрактов и покупке, запрета продажи аппаратуры/курьерского груза, нулевого баланса/остатка, невалидных входов, ошибок записи и одного действия за клик. Полный круг140, банкротство→подработка→возврат к торговле, JSON и миграция v1→v2, сохранение товаров при respawn, reset и все прежние быстрые регрессии. На storage event от другой вкладки блокировать запись и показывать предложение перезагрузки; конкурентная торговля явно вне объёма. Свежий критик проверяет фактическую игру, не только тесты.

## Предлагаемая схема новых полей

- `marketCargo`: список длиной0–2, `goodId` из components/ore/water, `purchasePrice` — целое1–1000000. Общий груз всех источников ≤2; без молчаливого удаления лишнего.
- `lastTrade`: null либо `{ sequence, kind, goodId, portId, price, basis, profit }`. Sequence — положительное безопасное целое; kind buy/sell, portId earth/mars, price/basis — целые1–1000000. У buy basis=price и profit=0, у sell profit=price-basis. Это результат сделки, расход при покупке показывается отдельно. Проверять безопасные пределы результата сложения/вычитания денег и sequence; исходный баланс — неотрицательное безопасное целое.
- `reliefContract`: `{ sequence: 0, status: "idle" }` по умолчанию. Idle→active только на Земле при completed основного контракта, credits<12 и пустом трюме. На принятии sequence увеличивается; active означает ровно1 единицу неприкосновенного курьерского груза. Active→idle только отдельной сдачей на Марсе с начислением30 одной транзакцией. Idle не выплачивает повторно; при балансе≥12 повторное принятие запрещено. Sequence сохраняется и валидируется как неотрицательное безопасное целое. UI хранит текущий sequence при создании действия, переход отклоняет несовпадение.
